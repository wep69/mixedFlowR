1 Purpose

A statistical package is not validated because its examples look plausible. Validation requires agreement with backend engines, known-design behavior, deterministic datasets and seeds, diagnostics, automated tests, dependency checks, and a reproducible local check workflow.

This vignette explains how to validate mixedFlowR without confusing documentation examples with evidence of numerical correctness.

2 1. Learning objectives

You will learn to:

  • distinguish static validation from runtime statistical validation;
  • inspect package capabilities and block coverage;
  • verify frozen teaching datasets;
  • reproduce seeds and simulation scenarios;
  • run unit and golden tests locally;
  • regenerate roxygen2 documentation and NAMESPACE;
  • run R CMD check through rcmdcheck;
  • validate optional backends separately;
  • document a validation session.

3 2. Validation layers

A useful validation hierarchy is:

  1. static integrity: files, exports, examples, placeholders, manifests;
  2. unit tests: functions return expected classes and safeguards;
  3. golden backend tests: wrappers agree with direct backend fits;
  4. design benchmarks: legacy and mixed representations align when theory says they should;
  5. simulation validation: known generating parameters are recovered with appropriate coverage;
  6. cross-platform checks: Windows, Linux, and supported R versions;
  7. scientific review: methods and interpretations remain defensible.

8 7. Golden test principle

A wrapper around lme4 should agree with direct lme4 fitting when both represent the same model.

Example test logic:

d <- mixed_data("longitudinal")

wrapped <- mixed_fit(
  height ~ treatment*time + (1|subject),
  d,
  engine = "lme4"
)

direct <- lme4::lmer(
  height ~ treatment*time + (1|subject),
  data = d
)

testthat::expect_equal(
  lme4::fixef(wrapped$model),
  lme4::fixef(direct),
  tolerance = 1e-8
)

Tests should compare quantities that are theoretically expected to agree, not merely visually similar output.

10 9. Safeguard tests are scientific tests

Examples include verifying that:

  • beta models reject 0/1 values when the selected family requires (0,1);
  • LRTs of different fixed-effect structures under REML are blocked;
  • missing optional backends produce informative errors;
  • bootstrap seeds are recorded;
  • contamination flags never delete observations automatically.

These are not cosmetic checks. They protect scientific interpretation.

11 10. Run the package tests

From the package root:

testthat::test_local()

For more diagnostic output:

testthat::test_local(reporter = "progress")

12 11. Regenerate roxygen2 documentation and NAMESPACE

The authoritative export/import source is the roxygen documentation in R/.

roxygen2::roxygenise()

Then inspect changes to:

  • NAMESPACE;
  • man/*.Rd;
  • any unexpectedly removed exports.

Do not hand-maintain a generated NAMESPACE in parallel with roxygen tags.

13 12. Load the source tree without installing

pkgload::load_all()

This is useful for development iteration. It does not replace installation and R CMD check.

14 13. Run R CMD check through rcmdcheck

rcmdcheck::rcmdcheck(
  args = c("--as-cran"),
  error_on = "warning"
)

Investigate every warning or note. Do not suppress a diagnostic merely to obtain a green badge.

15 14. Vignette evaluation policy

Most tutorial chunks use:

knitr::opts_chunk$set(eval = TRUE)

with optional backends guarded by requireNamespace().

Heavy chunks are intentionally eval=FALSE, including:

  • thousands of bootstrap refits;
  • production-scale Bayesian sampling;
  • deliberately failing safeguard examples;
  • examples that write persistent files during package build.

This policy keeps the documentation executable without making routine checks impractical.

16 15. Validate optional backends individually

A local validation matrix should include at least:

Backend Validation target
lme4 LMM/GLMM agreement and random structures
nlme AR1/CAR1/heterogeneity/NLMM
glmmTMB count, beta, ZI, Toeplitz, spatial covariance
robustlmm robust estimate agreement
confintROB BCa/wild interval routes
emmeans EMM/trend consistency
gamlss parameter extraction/quantiles
brms prior, posterior, PPC, LOO
SpATS field model and surface extraction
sommer MET and GxE covariance

17 16. Heavy validation should be separated from CRAN-style smoke tests

A simulation study for interval coverage or GxE recovery may take minutes or hours. Keep it in a dedicated validation script rather than forcing it into every unit-test run.

A reproducible heavy-analysis protocol should record:

  • scenario ID;
  • seed;
  • generating parameters;
  • number of simulations;
  • failed fit count;
  • convergence count;
  • bias;
  • RMSE;
  • interval coverage;
  • computing environment.

18 17. Simulation validation concept

For a parameter theta, assess:

  • bias: average estimate minus true value;
  • RMSE: root mean squared estimation error;
  • coverage: fraction of intervals containing the true value;
  • convergence/failure rate;
  • sensitivity to sample size and design imbalance.

Do not tune methods using only rejection rates or p-values.

20 19. Hashes and frozen artifacts

For archived validation, calculate file hashes for:

  • frozen datasets;
  • simulation inputs;
  • release tarball;
  • reference metadata;
  • key expected-output files if used as golden artifacts.

A hash detects unintended file change; it does not establish scientific validity.

21 20. Cross-platform validation

At minimum, validate on:

  • Windows with the intended user-facing R version;
  • a Linux CI environment;
  • the oldest supported R version where practical;
  • a current R-devel check for future compatibility.

Optional compiled backends may expose platform-specific issues that are invisible in static validation.

22 21. A local release gate

Before release, require:

  1. roxygen2::roxygenise() clean;
  2. testthat clean;
  3. static audit clean;
  4. heavy simulation battery reviewed;
  5. R CMD check --as-cran without unexplained warnings;
  6. all 20 vignettes render with expected optional-package behavior;
  7. README examples consistent with exported API;
  8. source archive inspected after extraction;
  9. reference metadata reviewed;
  10. package version and NEWS updated.

23 22. What this vignette does not claim

The presence of code in a vignette is not runtime validation evidence. The actual runtime environment must execute the relevant tests.

Likewise, passing R CMD check means the package satisfies important technical checks; it does not prove statistical optimality for every scientific application.

25 24. Key take-home messages

  • Static validation and runtime validation are different layers.
  • Wrappers should be tested against their authoritative backends.
  • Design benchmarks are as important as software benchmarks.
  • Seeds, versions, and frozen inputs are part of reproducibility.
  • Heavy simulation belongs in a separate validation battery.
  • R CMD check is necessary but not sufficient for scientific validation.
